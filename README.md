# Money Graph

Локальное рабочее место AML-аналитика для ответа на вопрос: **кого проверить первым и почему**. Проект строит воспроизводимую выгрузку из графа внутрибанковских переводов и показывает рассчитанные роли, приоритеты, кластеры и направленные связи.

Результат — очередь ручной проверки и объясняющие факты. Он не устанавливает виновность, не является вероятностью нарушения и не заменяет расследование.

## Что уже есть

- Контракт выгрузки v1.0.0: `src/contracts.py`.
- Аналитический pipeline: `pipeline.py`, `src/data.py`, `src/engine.py`, `src/reporting.py`.
- Независимый validator и Streamlit-интерфейс: `validate.py`, `app.py`.
- Тестовый синтетический bundle для проверки интерфейса: `tests/fixtures/ui/make_fixture.py`.
- Официальное описание входных parquet: [`data/README.md`](data/README.md).

Для оценки через приватный репозиторий исходные parquet включены в `data/`, а проверенный результат — в `outputs/`. После клонирования можно сразу проверить сохранённый bundle и открыть UI; повторный расчёт выполняется из тех же данных. `outputs/current.json` указывает на включённый в Git каталог `outputs/runs/<run_id>/` с тремя CSV, метриками, связями и manifest. Незавершённые staging-запуски и синтетические примеры в сдачу не входят.

## Вход и результат

Входные файлы размещаются в `data/`:

| Файл | Назначение |
| --- | --- |
| `nodes.parquet` | клиенты, глубина появления, seed-флаг |
| `edges.parquet` | агрегированные направленные пары переводов |
| `transactions.parquet` | отдельные переводы для сверки агрегатов |

Официальный набор содержит 2 248 клиентов, 3 119 направленных пар и 4 840 транзакций за июль 2026. Сбор ограничен исходящими ветвями от 81 seed, глубиной 4 и переводами от 5 000 KZT. Это неполная наблюдаемая выборка, а не история всех счетов.

Pipeline публикует единый неизменяемый bundle:

```text
outputs/
  current.json
  runs/<run_id>/
    run.json
    nodes_roles.csv
    clusters.csv
    top_nodes.csv
    node_metrics.parquet
    edges.parquet
```

Три CSV — артефакты для аналитика; parquet и manifest обеспечивают детальный разбор, направление связей и проверку целостности. `current.json` указывает на единственный опубликованный `run_id`; UI не смешивает файлы из разных запусков.

Подробная схема: [`docs/architecture.md`](docs/architecture.md). Сценарий показа: [`docs/demo.md`](docs/demo.md). Приёмочный протокол: [`docs/qa.md`](docs/qa.md).

## Запуск

### Docker (Windows, Linux, macOS)

Требуется Docker с Compose и Linux-контейнерами (на Windows — Docker Desktop).
Сборка выполняется один раз и после изменения кода/зависимостей:

```bash
docker compose build ui
```

Обычный запуск готового образа без сборки и скачивания:

```bash
docker compose up -d --no-build --pull never
```

Откройте http://localhost:3000. Эквиваленты: `make docker-build` и
`make docker-up`; на Windows — `.\make.cmd docker-build` и `.\make.cmd docker-up`.

Образ многостадийный: `builder` устанавливает закреплённые зависимости,
`runtime` получает готовое окружение и приложение. Тесты проекта, pytest и
неиспользуемые тестовые каталоги зависимостей исключены из рабочего образа
(модуль NumPy, который импортируется SciPy при работе, сохранён). Слой зависимостей
и кеш скачивания повторно используются при сборке после правок кода.
Python — 3.12.12, версии библиотек — из `requirements.lock`.

При пустом Docker volume сервис `prepare` запускает pipeline. При повторном
запуске он только проверяет сохранённую публикацию, включая SHA256 исходных
данных, и не пересчитывает роли. UI запускается после успешной проверки.
При повреждении результата или изменении входных данных запуск блокируется;
выполните явный пересчёт и снова запустите контейнеры. После обновления
аналитического кода также выполните пересчёт, чтобы получить новые результаты.

```bash
docker compose logs prepare
docker compose run --rm validate
docker compose run --rm --no-deps pipeline
```

Пересчёт доступен также как `make docker-recompute` / `.\make.cmd docker-recompute`.
После пересчёта нажмите «Обновить результаты» в интерфейсе.
Тесты имеют отдельный образ, который не собирается при обычном запуске:

```bash
docker compose build tests
docker compose run --rm tests
```

Или `make docker-test` / `.\make.cmd docker-test`.

Входной каталог `data/` подключён только для чтения и не входит в образ.
Результаты хранятся в Docker volume `money-graph_results`, отдельно от
Windows-каталога `outputs/`. UI читает их без права записи. CSV создаются
в Linux; Windows и Git не меняют окончания строк. `.gitattributes` защищает
также опубликованные файлы при последующих Git checkout; уже преобразованные
локальные файлы эта настройка автоматически не восстанавливает.

Остановка: `make docker-down`, `.\make.cmd docker-down` или `docker compose down`.
Результаты сохраняются; `docker compose down -v` удаляет volume с результатами.
Порт 3000 доступен только локально. Docker и запуск без Docker используют
один внешний порт: запускайте один вариант за раз.

### Без Docker

Быстрый запуск через GNU Make из корня проекта:

```bash
make setup
make run
```

В Windows установка GNU Make не требуется: используйте включённый `make.cmd` из CMD или PowerShell:

```powershell
.\make.cmd setup
.\make.cmd run
```

`setup` нужен при первой установке или изменении зависимостей; требуется доступный `uv`.
`run` последовательно рассчитывает реальные данные из `data/`, проверяет `outputs/` и запускает интерфейс на **http://localhost:3000**. При ошибке следующий шаг не запускается. Остановка сервера — Ctrl+C.

Для просмотра уже включённых результатов без пересчёта: `make ui` (Windows: `.\make.cmd ui`). Остановить UI: `make stop` (Windows: `.\make.cmd stop`). Для другого порта: `make stop PORT=3001`. Другие команды: `pipeline`, `validate`, `test`, `demo`, `help`. Только `demo` использует синтетические данные.

Если сохранённый bundle выдаёт ошибку SHA256, выполните `make run` (Windows: `.\make.cmd run`): он создаст новый проверенный результат из исходных parquet.

GNU Make принимает параметры, например `make ui PORT=3001 OUTPUTS=outputs`. Для `make.cmd` параметры `PORT`, `DATA`, `OUTPUTS` задаются переменными окружения (PowerShell: `$env:PORT = "3001"`).

Требуется Python 3.10+; полный запуск проверен на Python 3.13.15 с версиями библиотек из `requirements.txt`. Зависимости также зафиксированы в `requirements.lock`.

```bash
uv venv .venv
uv pip sync --python .venv/bin/python requirements.lock
```

Полный расчёт из корня проекта:

```bash
.venv/bin/python pipeline.py --data data --out outputs
.venv/bin/python validate.py --data data --out outputs
./run-ui.sh --outputs outputs
```

В Windows PowerShell из корня клонированного репозитория:

```powershell
.\.venv\Scripts\python.exe pipeline.py --data data --out outputs
.\.venv\Scripts\python.exe validate.py --data data --out outputs
.\.venv\Scripts\python.exe -m pytest -q
```

Validator и UI не пересчитывают роли при открытии результатов. Для малого синтетического набора передайте одинаковый `--expected-nodes N` в pipeline и validator; такой запуск явно помечается `data_kind=synthetic`.

Для проверки интерфейса без реальных данных создайте явно помеченный synthetic bundle:

```bash
.venv/bin/python tests/fixtures/ui/make_fixture.py --out demo_outputs --data demo_data
.venv/bin/python validate.py --data demo_data --out demo_outputs --expected-nodes 24
./run-ui.sh --outputs demo_outputs
```

Synthetic-данные нужны только для UI/протокола и не должны демонстрироваться как аналитический результат.

## Методология

Каждому клиенту назначается одна из шести ролей: `consolidator`, `distributor`, `transit`, `terminal`, `coordinator` или `peripheral`. Содержательные роли определяются сочетанием степеней, объёмов, числа переводов и структурных метрик; `peripheral` означает отсутствие достаточно выраженного паттерна в доступной выборке.

Приоритет ручной проверки — взвешенная сумма четырёх нормированных компонентов: структура (0.35), близость к seed (0.20), масштаб потоков (0.30), поддержка ролью (0.15). Балл и уверенность в роли лежат в диапазоне [0, 1], но не являются вероятностями. Нормализация и пороги выводятся из входных данных и сохраняются в `run.json`.

Оговорки обязательны:

- `depth=4` — граница обхода; отсутствие исходящего перевода не означает конечного получателя.
- Для seed входящий поток неполон; отношение входа/выхода не используется как основание для вывода.
- Переводы ниже 5 000 KZT и связи за пределами исходящих ветвей seed не наблюдаются.
- Роль — объяснимая гипотеза для приоритизации проверки, а не ярлык клиента.

Точные формулы, поля и правила разрешения пересекающихся ролей заданы в [`PLAN.md`](PLAN.md) и в контракте `src/contracts.py`.
Проверка реальных ролей, объяснений и чувствительности порогов записана в [`AUDIT_LANE_A.md`](AUDIT_LANE_A.md).

## Приёмка

Перед демо нужно выполнить [QA-протокол](docs/qa.md). В этом workspace независимый validator вернул `passed`: 2 248 клиентов, 3 119 связей, 105 кластеров, 35 компонент и 20 строк Top. Два запуска дали одинаковые CSV и метрики; время от чтения до candidate-проверки составило 2,38 и 2,27 с. Streamlit AppTest открыл реальный bundle без исключений. После аудита объяснений повторный запуск также прошёл validator и все 61 тест:

1. Запустить pipeline в чистом окружении и зафиксировать фактическое время (требование: менее 300 секунд).
2. Запустить независимый validator на опубликованном bundle.
3. Убедиться, что есть 2 248 строк ролей, минимум 20 уникальных Top-узлов, кластеры покрывают всех клиентов, а manifest имеет статус `complete` и `validation.passed`.
4. Проверить в UI три произвольных `gid`, boundary-узел и изолированный seed; сопоставить карточку со строками выгрузки и направлением рёбер.

## Масштабирование

Текущая реализация рассчитана на предоставленный набор. Для порядка миллиона узлов потребуется перейти от графа в памяти к CSR/специализированному graph engine, читать parquet пакетами, применять приближённые centrality/community-алгоритмы и выдавать заранее рассчитанные метрики с ограниченным ego-графом. Это план развития, не заявленная реализованная возможность.
