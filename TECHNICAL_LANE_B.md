> После слияния `origin/main` получен авторитетный контракт A `src/contracts.py` версии **1.0.0**. Ниже описан работающий прототип B с числовой версией **1** и плоским каталогом. Его адаптация ещё требуется: `counts.nodes`, `current.json` → `runs/<UUID>`, завершённый status/validation и `--candidate`. Старый fixture и 23 теста проверяют прототип, а не соответствие новому контракту. Не считать это слияние завершённой интеграцией A/B.

Реализованы UI и validator. Реальная выгрузка Lane A пока отсутствует: работу полного parquet→CSV pipeline этот документ не подтверждает. Корневой README и расчётные файлы Lane A не изменены. Материал ниже можно передать владельцу README.

## Запуск

Из корня репозитория, Python 3.12 (проверенная версия окружения):

```bash
uv venv .venv
uv pip sync --python .venv/bin/python requirements.lock
./run-ui.sh --outputs outputs
```

Без uv: создать venv средствами Python и выполнить `.venv/bin/python -m pip install -r requirements.lock`. Установка требует доступа к пакетам; после установки интерфейс работает локально, без внешних API, CDN и телеметрии Streamlit.

Проверка настоящего результата Lane A:

```bash
.venv/bin/python validate.py --data data --out outputs
.venv/bin/python validate.py --data data --out outputs --bundle
```

Первая команда проверяет три CSV независимо от engine/manifest и подходит для проверки перед публикацией `run.json`. Вторая дополнительно проверяет UI bundle. При ошибке exit=1 с причиной; при успехе — JSON отчёт. По умолчанию требуется ровно 2248 клиентов; `--expected-nodes` предназначен для отдельных тестовых наборов.

## Передача от Lane A

Читатель реализует таблицы из PLAN.md. Ниже конкретный ожидаемый формат manifest для согласования с A (новый `src/contracts.py` Lane B не создаёт).

В каталоге outputs должны находиться:

- `nodes_roles.csv`: gid, role, role_score, cluster_id, priority_score, evidence.
- `clusters.csv`: cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis.
- `top_nodes.csv`: rank, gid, role, priority_score, why.
- `node_metrics.parquet`: gid, depth, is_seed, in_deg, out_deg, in_kzt, out_kzt, in_tx, out_tx, pagerank. Значения в именах starter. Полезные дополнительные колонки: component_id, betweenness, score каждой роли, alternative/margin, ratio_usable, priority-компоненты. Неизвестные дополнительные признаки доступны в карточке. Если component_id отсутствует, UI вычисляет компоненты только для навигации.
- `edges.parquet`: src, dst, sum_kzt, n_tx, depth — исходная схема.
- `run.json`, публикуемый последним после записи файлов.

Минимум для чтения manifest:

```json
{
  "schema_version": 1,
  "n_nodes": 2248,
  "output_sha256": {
    "nodes_roles.csv": "<SHA256 bytes>",
    "clusters.csv": "<SHA256 bytes>",
    "top_nodes.csv": "<SHA256 bytes>",
    "node_metrics.parquet": "<SHA256 bytes>",
    "edges.parquet": "<SHA256 bytes>"
  }
}
```

Поля provenance, runtime, thresholds, input hashes, versions и warnings из PLAN.md также сохраняются A и показываются в диагностике; это не обязательные поля минимального UI reader. Для synthetic fixture дополнительно `data_kind: "synthetic"`. Хеши проверяются по прочитанным байтам, UI не смешивает их с файлами из input data. При отсутствии/повреждении manifest выводится ошибка, не старый результат.

CSV читается без float-преобразования gid. Cluster_id — неотрицательное целое. `top_gids` — до пяти gid через `|`, в порядке priority desc / числовой gid asc. Top CSV использует тот же порядок. Поле evidence содержит цифры и не превышает 200 Unicode-символов. Seed не получает transit в P0 согласно PLAN.md; terminal запрещён на depth=4 и при наличии выхода/отсутствии входа.

Validator проверяет покрытие узлов, суммы кластеров, seed, сортировку, согласованность Top, компоненты и степени/суммы UI metrics. Он не доказывает корректность классификатора, не воспроизводит все формулы ролей и не заменяет тесты engine Lane A. Если A меняет контракт, нужны синхронная правка читателя и тестовый bundle.

## Что проверять руками

1. Запустить UI, убедиться в корректном источнике и пометке synthetic, если это пример.
2. Ввести любой gid; длинные идентификаторы не должны округляться.
3. Выставить фильтр priority=1 и найти существующий gid: карточка откроется независимо от фильтра с пояснением.
4. Проверить seed, boundary, изолят и неизвестный gid; исключений быть не должно.
5. На вкладке разбора сравнить направление стрелок и суммы с полными таблицами входа/выхода.
6. Сравнить CSV со скачанными файлами; они должны совпадать побайтово.

Обзор показывает сообщества, содержащие подходящих под фильтры клиентов, с полными размерами. До 100 сообществ, до 100 клиентов ego, до 350 рёбер на графике; сокращение явно обозначено. Полные прямые связи выбранного узла не сокращаются. Один/два шага определяются по соседству в обе стороны, сами рёбра остаются направленными. Выбор клиента — через точный поиск или список; наведение на граф показывает сведения.

Проверяются: повреждённые хеши, отсутствующие/повторные gid, неправильные роли/оценки/evidence, ошибочные суммы/seed/top_gids кластеров, Top-сортировка, глубина/seed, согласованность metrics, направленный ego, изолят, точность int64, CLI и сценарии Streamlit AppTest. Реальная интеграция с 2248 рассчитанными ролями остаётся пунктом приёмки после передачи Lane A.


## Проверено при передаче

- Все 23 pytest/AppTest проверки прошли, в том числе в отдельном окружении, установленном из `requirements.lock` без сети из локального кеша.
- Streamlit health endpoint ответил `ok`; реальный Chromium проверил boundary, изолята и неизвестный gid без JavaScript page errors. Поиск boundary на синтетическом примере занял около 1.9 секунды на текущей машине.
- Построение ego на реальной топологии 2248 узлов: 100 показанных узлов, 101 ребро, около 0.16 секунды. Это только замер геометрии с временными атрибутами в памяти, не результат классификации или замер полного pipeline.
- Для необязательной проверки реальным браузером: установить Playwright и Chromium отдельно от зависимостей приложения, запустить UI с `demo_outputs`, затем `python tests/browser_smoke.py`. Скрипт ожидает именно синтетический fixture; снимок сохраняется в `/tmp`.
