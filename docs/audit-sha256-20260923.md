# Аудит ошибки SHA256 при открытии результата Lane A

Дата: 2026-09-23. Проверен HEAD `8841dfc` и публикация
`00e4ed69-15c5-4c87-b3cb-ea4a1e44ac57`, указанная в `outputs/current.json`.
Текст скриншота использован как свидетельство ошибки, а не как инструкция.

## Вывод

Ошибка воспроизведена. Причина в рабочей копии — замена LF на CRLF в трёх
CSV при выдаче файлов Git на Windows. Изменения значений метрик или ролей
этой ошибкой не подтверждаются. Блокировка интерфейсом соответствует
контракту побайтовой целостности; сообщение «смешанные/повреждённые
результаты» не устанавливает причину и не доказывает ошибку автора Lane A.

## Доказательства

- `git config --show-origin --get core.autocrlf`: системная настройка `true`.
- `git ls-files --eol outputs`: у CSV `i/lf w/crlf`; атрибуты для них не заданы.
  Отслеживаемого `.gitattributes` нет.
- Все пять output-файлов, прочитанных напрямую через `git show HEAD:<path>`,
  имеют SHA256, указанные в `run.json`.
- В рабочей копии не совпадают только три CSV. Простая замена байтов CRLF
  на LF возвращает каждому точный ожидаемый SHA256. Число замен:
  `nodes_roles.csv` — 2249, `clusters.csv` — 106, `top_nodes.csv` — 21.
- Оба выходных Parquet и все три входных Parquet совпадают с manifest
  без преобразований. Метрики `node_metrics.parquet` не повреждены.
- В пяти остальных локальных каталогах запусков все output-хеши совпадают
  с их manifest; текущий указатель выбирает именно опубликованный в Git запуск.

Для `nodes_roles.csv`:

```text
run.json / Git blob / рабочая копия после CRLF→LF:
19dd979db4cbe02f5daa71fce534facf9c18c83ff7aa7408e3104280a507d9e0
рабочая копия до преобразования:
e9ffb02c7aed22cf8a74beab9d2df21775f0e8bd6eb7165eb588c5542904c454
```

Публикация результатов в Git добавлена коммитом `afa2f35`.
Это указывает на этап доставки, на котором появилась возможность
преобразования окончаний строк, но не устанавливает персональную вину.

## Проверки

1. `python validate.py --data data --out outputs` воспроизводит ошибку
   SHA256 на `nodes_roles.csv` (код выхода 1).
2. Все файлы текущего запуска извлечены побайтово из Git во временный
   каталог. Тот же validator с этим каталогом вернул `passed`, код 0:
   2248 узлов, 3119 рёбер, 81 seed, 105 кластеров, Top-20,
   35 компонент, 19 изолятов. Проверены также входные файлы.
3. `python -m pytest -q`: **61 passed in 20.71s**.
4. Текущий pipeline повторно запущен на `data/` во временном каталоге.
   Новая публикация прошла встроенную валидацию. Сравнение всех столбцов
   всех пяти файлов с исходным Git-пакетом показало одинаковые роли,
   идентификаторы, кластеры, evidence, ранги Top-20 и исходные графовые
   показатели. Отличаются только некоторые вычисляемые float, максимум
   `2.220446049250313e-16`. `clusters.csv` и `edges.parquet` совпали побайтово.
   Python исходного запуска — 3.12.12, локального — 3.13.15;
   версии пяти библиотек из manifest совпадают. Поэтому побайтовую
   идентичность нового вычисления старому не заявляем.

## Рекомендации

- Для хешируемых артефактов запретить Git преобразовывать содержимое,
  например атрибутом `outputs/runs/** -text`, затем восстановить текущие CSV
  из проверенных Git blob побайтовым API. Перед заменой проверять хеш
  исходных blob против manifest. Более узкая альтернатива для нынешних
  LF-экспортов: `outputs/runs/**/*.csv text eol=lf`.
- Сохранять строгую проверку SHA256. Не переписывать manifest под изменённые
  файлы и не отключать защиту интерфейса.
- В сообщении интерфейса уточнить, что несовпадение может означать
  преобразование файлов при Git checkout или копировании. Общий текст
  «Нет завершённого расчёта» неточен для существующего завершённого пакета,
  который не прошёл проверку целостности.
- Проверять доставку опубликованного пакета на Windows с
  `core.autocrlf=true`; обычные тесты pipeline во временных каталогах
  не воспроизводят Git checkout.

В рамках аудита исходный код, настройки Git, `current.json` и результаты
не изменялись. Создан только этот отчёт. Временные проверочные каталоги
удалены. Вывод относится к доступной рабочей копии: среда, из которой
сделан скриншот, отдельно не исследовалась. Проверка не является оценкой
точности AML-классификации по размеченной выборке.

## Последующее исправление по запросу пользователя

После завершения аудита добавлены Dockerfile, Compose, `.dockerignore`
и `.gitattributes`. Pipeline создаёт результат в Docker volume, UI читает
его только для чтения и запускается после успешной публикации. Исходные
данные подключаются только для чтения и не входят в образ.

Три CSV и `run.json` старого локального запуска восстановлены побайтово
из HEAD после проверки, что различия ограничены окончаниями строк;
значения manifest не пересчитывались. Локальная валидация прошла.
В отдельном временном Git-репозитории проверен checkout с
`core.autocrlf=true`: новые атрибуты сохраняют все три CSV побайтово.

Docker-образ собран, `docker compose up --build -d` выполнен. Pipeline
завершился с кодом 0, сервис UI имеет статус healthy. Независимая
валидация Docker-публикации прошла на 2248 узлах. Все 61 тест в Docker
прошли за 17,13 с. Streamlit AppTest открыл фактический Docker-результат
без исключений и сообщений об ошибках; health endpoint вернул `ok`.
Подтверждено, что volume UI смонтирован с `RW=false`.
