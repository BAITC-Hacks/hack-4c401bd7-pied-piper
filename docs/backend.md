# Backend Money Graph

Реализован локальный API `/api/v1` и отдельный worker для
[контракта](frontend-contract.md). Новый frontend не реализовывался:
существующий Streamlit читает свои bundle напрямую, без этого API.

## Запуск

Из корня репозитория в Windows:

```powershell
uv pip sync --python .venv/Scripts/python.exe requirements.lock
.\.venv\Scripts\python.exe -m backend
```

Эквивалент: `.\make.cmd backend`. На Linux/macOS: `.venv/bin/python -m backend`
или `make backend`. Команда запускает API на `127.0.0.1:8000` и дочерний worker;
Ctrl+C завершает оба процесса. Другой порт: `python -m backend --port 8001`.

- Health: `http://127.0.0.1:8000/api/v1/health` — доступность API и БД.
- OpenAPI JSON: `http://127.0.0.1:8000/openapi.json`.
- Swagger: `http://127.0.0.1:8000/docs` (ресурсы Swagger загружаются с CDN;
  API, JSON-схема и расчёт не требуют CDN или LLM).

Первый старт копирует входы и готовый проверенный bundle в собственное хранилище.
Повторный старт не создаёт дубли. При отсутствии bundle регистрируется только
официальный датасет; расчёт запускается через API. Повреждённый существующий
bundle блокирует bootstrap: требуется явный пересчёт CLI, без скрытой подмены.

Отдельные процессы с одинаковыми переменными окружения:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.api:create_app --factory --host 127.0.0.1 --port 8000
# В другом терминале:
.\.venv\Scripts\python.exe -m backend.worker
```

Docker, только API и worker:

```bash
docker compose --profile backend up -d --build api worker
docker compose logs api worker
docker compose stop api worker
```

Порт опубликован на loopback, исходные данные подключены read-only, состояние
хранится в volume `backend-state` (обычно `money-graph_backend-state`). Stop
сохраняет данные. Существующий запуск Streamlit остаётся доступен отдельно.

## Конфигурация и хранение

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| MONEY_GRAPH_STATE | `<repo>/runtime` | SQLite, снимки входов и результаты worker |
| MONEY_GRAPH_DATA | `<repo>/data` | Доверенный набор для bootstrap и профиля импорта |
| MONEY_GRAPH_OUTPUTS | `<repo>/outputs` | Исходный готовый bundle |
| MONEY_GRAPH_BOOTSTRAP | `1` | `0` отключает регистрацию исходных данных для отдельных сред/тестов |

SQLite: WAL, внешние ключи, BEGIN IMMEDIATE при изменении очереди, уникальные
ограничения на idempotency key и активный run датасета. Схема автоматически
создаётся с user_version=1; неизвестная версия блокирует открытие.

```text
runtime/
  registry.sqlite3
  datasets/<dataset_id>/{nodes,edges,transactions}.parquet
  results/.staging/<run_id>/...
  results/runs/<run_id>/...
  results/current.json
```

API обращается к конкретному run_id, проверяет manifest/SHA256 при чтении и не
выбирает другой run при ошибке. current.json не переключает открытые API-карточки.
Изменяемый selection хранится отдельно от аналитики и привязан к run_id.
В разных вкладках действует последняя запись, согласно контракту.

Резервная копия: остановить API и worker, скопировать весь MONEY_GRAPH_STATE,
включая SQLite WAL-файлы, если они присутствуют, затем запустить процессы.
Восстановление: полный согласованный снимок в прежний MONEY_GRAPH_STATE и совместимая
версия кода (реестр хранит абсолютные пути). Перенос на другой путь требует миграции путей.
Копирование одного registry.sqlite3 при работающем worker не является резервной
копией. В Docker копируется весь volume при остановленных api/worker.
Автоматическая ротация резервных копий не реализована.

## Границы импорта

POST `/datasets`: name, profile=hackathon-v1 и файлы nodes/edges/transactions.
Лимит 50 MiB на файл; транспорт 151 MiB, включая chunked-запросы. Остальные тела
API ограничены 1 MiB. Пользовательское имя файла не используется как путь хранения.

Worker проверяет текущим загрузчиком схемы, идентификаторы, даты июля 2026,
ссылки, суммы и количество транзакций, затем SHA256 относительно доверенного
MONEY_GRAPH_DATA. **v1 принимает повторную загрузку официальных файлов, а не
произвольные новые банковские наборы.** Другая запись тех же таблиц в Parquet может
иметь другой хеш и будет отклонена. Универсальный импорт требует нового профиля,
метаданных периода/сбора и изменения проверок аналитического ядра.

data_kind нельзя задавать из HTTP. Синтетический bundle может быть явно
зарегистрирован bootstrap в тестовой среде с соответствующими входами/результатом;
публичный импорт не присваивает небольшому файлу статус synthetic или official.

## Расчёты и восстановление

POST `/runs` требует Idempotency-Key UUID. Тот же key/body возвращает тот же run,
в том числе завершённый; другой body — конфликт. На датасет допускается один
queued/running. Повторный расчёт после завершения получает новый ключ.

Worker сообщает load/features/roles/export/validation/publish и устанавливает
succeeded только после проверки и публикации целого результата. UUID API,
manifest и каталога совпадает. Клиентские gid всегда строки; неопределённые
отношения представлены null, суммы — конечными числами в KZT.

Heartbeat обновляется каждые 2 секунды. После отсутствия heartbeat более 120 секунд
другой/перезапущенный worker атомарно забирает восстановление. Целый опубликованный
bundle повторно проверяется и регистрируется succeeded, иначе run становится failed.
Зависшая проверка датасета становится failed. Повтор создаёт новый run/импорт.
Публикация защищена проверкой владельца под блокировкой SQLite, чтобы потерявший
задание worker не публиковал результат.

Runtime API включает ожидание очереди; manifest сохраняет отдельный тайминг
аналитики и ограничение <300 секунд. Аварийные staging-файлы не показываются как
готовые результаты. Автоматическая очистка staging/старых импортов и ограничение
общего занятого места пока не реализованы.

## Проверка

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m pytest tests/test_backend.py -q
# При работающих API и worker:
.\.venv\Scripts\python.exe scripts/smoke_backend.py --base-url http://127.0.0.1:8000/api/v1/ --data data
```

HTTP smoke создаёт новый импорт и run, проверяет повтор ключа, три карточки/графа,
selection и четыре экспорта. Существующие данные не удаляет. Требует официальные
входы. Обязательные артефакты по-прежнему проверяются через backend/validate.py.
Docker tests подключает data/outputs read-only для теста реального расчёта.

Нет авторизации, совместных расследований и интеграции нового frontend. Сервер
предназначен для локального доступа. Для многих пользователей нужны модель доступа,
согласование одновременных изменений и пересмотр хранения/индексов. Для значительно
большего графа потребуются индексированные представления и проверяемый кеш;
нынешний API повторно проверяет небольшой bundle при чтении.
