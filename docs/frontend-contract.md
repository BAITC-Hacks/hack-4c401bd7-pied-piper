# Контракт frontend ↔ backend Money Graph

Версия предложения: **1.0.0**, 23 сентября 2026.

**Статус: backend API реализован; новый frontend не реализован.**
Запуск и границы профиля: [backend.md](backend.md). Документ фиксирует поведение API
и целевое поведение frontend хакатонной версии. Существующие `frontend/app.py`
(Streamlit), pipeline и CSV продолжают работать по текущему протоколу.
Типы запросов и ответов: [frontend-api.types.ts](frontend-api.types.ts).
Версия API не заменяет `SCHEMA_VERSION` файлового bundle из `backend/core/contracts.py`.

## 1. Цель и границы

Основной сценарий: загрузить три Parquet → проверить → запустить расчёт → открыть
очередь приоритетов → разобрать любой gid и его связи → выбрать клиентов для
углублённой проверки → скачать перечень и обязательные CSV.

Первая версия — локальное рабочее место одного аналитика. Нет регистрации,
паролей, многопользовательских дел, редактирования рассчитанных ролей, чат-бота,
внешних источников и банковских интеграций. Доступ из внешней сети без отдельного
решения по аутентификации не входит в этот контракт.

Импорт принимает профиль `hackathon-v1`: существующую схему и параметры сбора
из `data/README.md`. Это не универсальный импорт любых банковских данных.
Основной экран предлагает также уже подготовленный официальный датасет, чтобы
демонстрация не зависела от повторной загрузки файлов.

## 2. Ответственность сторон

| Backend | Frontend |
| --- | --- |
| Проверяет файлы, схемы, суммы, типы и ссылки | Проверяет наличие трёх файлов и предварительный лимит размера |
| Рассчитывает роли, метрики, кластеры и приоритеты | Показывает полученные значения, округляет только для отображения |
| Валидирует и публикует целый результат | Не показывает частичный результат как завершённый |
| Фильтрует, сортирует, ограничивает граф, формирует CSV | Управляет фильтрами, выбором клиента и размещением узлов на экране |
| Хранит задания, датасеты и список на проверку | Восстанавливает экран из URL; не считает localStorage источником результата |
| Возвращает предупреждения о неполноте | Показывает предупреждения рядом с выводами |

Frontend не пересчитывает роли, рейтинг, кластеры и степени по усечённому графу.
Расчёт позиций для отрисовки графа допустим. API отдаёт данные, а не Plotly HTML.

## 3. Общие правила API

- Базовый путь: `/api/v1`; рекомендуемая схема развёртывания — frontend и API
  одного origin. В разработке frontend использует proxy для `/api`.
- JSON UTF-8. Одиночный ресурс возвращается объектом без обёртки `data`.
  Списки — `Page<T>`, списки аналитики — `RunPage<T>`.
- Все идентификаторы клиента `gid`, `src`, `dst`, элементы `top_gids` — строки,
  в том числе если число помещается в JavaScript Number. Нельзя применять
  `Number`, `parseInt` или хранить ID как число. `cluster_id` и `component_id` — числа.
- `dataset_id` и `run_id` — канонические UUID. URL кодируется обычными средствами
  маршрутизатора. Backend не принимает файловые пути вместо идентификаторов.
- `gid` в URL — каноническая десятичная строка int64: `0` или число без ведущих
  нулей и `+`, допускается `-` для отрицательного int64. Frontend убирает только
  внешние пробелы; backend проверяет диапазон без преобразования в float.
- Суммы — конечные JSON numbers в KZT, без строк форматирования. Это наблюдаемые
  потоки, а не бухгалтерские остатки. Доли и scores — числа от 0 до 1.
- `null` означает неизвестное/неопределённое; 0 означает наблюдаемый ноль.
  `NaN` и Infinity запрещены. Даты `YYYY-MM-DD`, время RFC3339 UTC с `Z`.
- Все поля типов обязательны, если не помечены `?`. Nullable-поля присутствуют
  со значением `null`. Новые необязательные поля допустимы в v1; удаление/смена
  типа поля и изменение смыслов требуют новой основной версии.
- Пагинация: `limit=50`, максимум 200, `offset=0`; положительный целый limit,
  неотрицательный offset. `total` — число после фильтров до пагинации.
  Offset за концом возвращает пустой `items`, HTTP 200.
- Неизвестные query-параметры и недопустимые enum возвращают 422.
- HTTP-заголовок `X-Request-ID` присутствует во всех ответах. Ошибки используют
  тот же ID в JSON. Не возвращать stack trace, локальные пути или секреты.
- При загрузке/обновлении списков frontend отменяет устаревшие запросы либо
  игнорирует их ответы. Cache key включает run_id и все фильтры.
- После выбора run все аналитические запросы содержат его ID. Новый расчёт
  не переключает открытые карточки и не смешивает результаты автоматически.

## 4. Экраны и маршруты frontend

| URL | Содержание | Обязательные состояния |
| --- | --- | --- |
| `/datasets` | Датасеты, импорт, готовый официальный набор | загрузка, пусто, ошибка, список |
| `/datasets/:datasetId` | Проверка файлов, ошибки, запуск и история расчётов | validating / ready / invalid / failed |
| `/runs/:runId` | Обзор: counts, роли, граф кластеров, переход в Top | queued / running / failed / succeeded |
| `/runs/:runId/nodes` | Все клиенты, фильтры, поиск точного gid | loading, empty, error, ready |
| `/runs/:runId/top` | Глобальный Top текущего запуска | loading, error, ready |
| `/runs/:runId/nodes/:gid` | Карточка, объяснение, граф 1–2 шага, полные прямые связи | loading, not_found, error, ready |
| `/runs/:runId/clusters` | Таблица кластеров; выбор кластера открывает его клиентов | loading, empty, error, ready |
| `/runs/:runId/selection` | Выбранные клиенты и скачивание перечня | loading, empty, saving, error, ready |

Фильтры списка сохраняются в query URL. Точный поиск открывает карточку независимо
от фильтров. Возврат в список сохраняет фильтры и страницу. Неуспешный точный поиск
показывает «Клиент не найден в этом расчёте», а не пустую карточку.

## 5. Импорт и датасеты

| Метод / путь | Запрос | Ответ |
| --- | --- | --- |
| `POST /datasets` | multipart/form-data, см. ниже | 202 `Dataset`, `Location: /api/v1/datasets/{id}` |
| `GET /datasets` | limit, offset | 200 `Page<Dataset>`, новые первыми, затем dataset_id |
| `GET /datasets/{dataset_id}` | — | 200 `Dataset` |

Multipart-поля: `name` (1–120 символов после trim), `profile` (только `hackathon-v1`),
`nodes`, `edges`, `transactions` (ровно по одному файлу `.parquet`). Сопоставление
определяется именем поля; исходное имя файла не используется как путь хранения.
Лимит v1 — 50 MiB на файл и 150 MiB суммарного содержимого файлов; транспорт
допускает до 151 MiB с multipart overhead. Превышение — 413. Расширение/тип
загрузки проверяется предварительно, реальное содержимое проверяет backend.

Состояния: `validating → ready | invalid | failed`. `invalid` — дефект содержимого;
`failed` — технический сбой обработки. Для invalid заполнены validation.errors,
для failed — failure. Загрузка сохраняет собственный снимок файлов и не меняет
существующий датасет. Для исправления выполняется новый импорт.

`counts` и `period` равны null до успешной проверки; period берётся из транзакций.
`collection` задаётся профилем: 4 колена, 5000 KZT, исходящее направление.
Произвольный пользовательский ввод этих параметров в v1 отсутствует.
`data_kind` определяет backend; multipart не позволяет объявить данные официальными.
Официальный профиль сверяет параметры и состав с предоставленным набором;
synthetic доступен для зарегистрированных backend тестовых fixtures и всегда
помечается в интерфейсе. Продуктовый импорт произвольных размеров — последующий контракт.

Frontend опрашивает validating раз в 2 секунды; прекращает polling на терминальном
состоянии или при уходе со страницы. Progress загрузки байтов можно показывать,
проверку после загрузки — как отдельное состояние без выдуманного процента.
После ready доступны кнопка расчёта и история запусков.

## 6. Запуски

| Метод / путь | Запрос | Ответ |
| --- | --- | --- |
| `POST /runs` | `CreateRunBody`, заголовок `Idempotency-Key: UUID` | 202 `Run`, Location ресурса |
| `GET /runs` | dataset_id (обязателен), limit, offset | 200 `Page<Run>`, created_at DESC, run_id ASC |
| `GET /runs/{run_id}` | — | 200 `Run` |
| `GET /runs/{run_id}/summary` | — | 200 `RunSummary` |

Начальный запрос: `{ "dataset_id": "00000000-0000-4000-8000-000000000001" }`.
Idempotency-Key создаётся один раз на намерение запуска. Сетевой повтор отправляет
тот же ключ и body и получает тот же run (202), даже если он уже завершён.
Тот же ключ с другим body — 409 IDEMPOTENCY_CONFLICT. Ключ хранится с запуском.
Другой ключ при активном запуске того же датасета — 409 ACTIVE_RUN_EXISTS с
related_run_id. Повторный расчёт после завершения получает новый ключ и новый run.

Состояния: `queued → running → succeeded | failed`; queued также может стать failed
при невозможности выполнения. stage заполнен только при running. После сбоя
запуск не возвращается в running: явный повтор создаёт новый run. Перезапуск
worker должен завершать потерянные running-задания понятной ошибкой.

Стадии: load → features → roles → export → validation → publish. Frontend показывает
текущую стадию и elapsed_seconds; точный процент и ETA контракт не обещает.
Polling раз в 2 секунды, без параллельных запросов к одному run. При сетевой ошибке
показать потерю связи и повторять с задержкой до 10 секунд; не объявлять run failed
из-за сетевой ошибки браузера. После succeeded загрузить summary.

`succeeded` разрешён только после независимой проверки и публикации всего bundle.
API заранее выделяет run_id; worker должен записать тот же ID в manifest и путь
bundle. Это требует адаптации текущего pipeline, где UUID создаётся внутри расчёта.
Для ранее рассчитанного bundle backend регистрирует существующий run_id и датасет.
API elapsed_seconds включает очередь и публикацию; измерение аналитического runtime
в manifest сохраняется отдельно и используется для проверки требования пяти минут.

Все аналитические endpoints до succeeded возвращают 409 RUN_NOT_READY. Если
готовые файлы повреждены — 503 RESULT_INVALID, без подмены другим запуском.
`summary.thresholds`, веса и methodology_version относятся именно к этому run.

## 7. Клиенты, рейтинг, кластеры

| Метод / путь | Query | Ответ |
| --- | --- | --- |
| `GET /runs/{run_id}/nodes` | `NodeQuery` | `RunPage<NodeSummary>` |
| `GET /runs/{run_id}/nodes/{gid}` | — | `NodeDetail` |
| `GET /runs/{run_id}/top` | limit, offset | `RunPage<RankedNode>` |
| `GET /runs/{run_id}/clusters` | limit, offset | `RunPage<Cluster>` |
| `GET /runs/{run_id}/clusters/{cluster_id}` | — | `ClusterDetail` |
| `GET /runs/{run_id}/nodes/{gid}/edges` | `EdgeQuery` | `RunPage<Edge>` |

Все успешные ответы — HTTP 200. Неизвестный run/node/cluster — 404 NOT_FOUND.
Пустой отфильтрованный список — 200. Параметры node list:

- `role=transit&role=consolidator`: OR внутри ролей; остальные фильтры объединяются AND.
- `cluster_id`, `component_id`: целые ≥0; `min_priority`: [0,1].
- `is_seed`, `at_boundary`: `true` / `false`, отсутствие — не фильтровать.
- `sort`: priority_desc (по умолчанию), role_score_desc, gid_asc.
  При равных scores — числовой gid ASC на backend, без преобразования ID браузером.

Top отражает сохранённый `top_nodes.csv`: глобальный rank, why и порядок из файла,
total равен числу строк файла. Default limit=20, max=200. Фильтры сюда не применяются;
для отфильтрованной очереди используется nodes. Frontend не перенумеровывает rank.
Clusters сортируются по n_nodes DESC, cluster_id ASC; top_gids преобразуется из
CSV-строки в массив строк. component_id определяется по принадлежности узлов.

Прямые связи: direction=in для dst=gid, out для src=gid, both (по умолчанию) —
объединение без повторов. Сортировка sum_kzt DESC, затем src и dst как числовые ID.
Это полный список наблюдаемых прямых связей с пагинацией, независимо от усечения графа.

Карточка включает суммы, количества транзакций, степени, альтернативную роль,
числовое evidence, поддержки пяти содержательных ролей и четыре вклада в приоритет.
`role_support` адаптируется из eligible_*, score_*, ineligible_reason_* текущих метрик.
`priority.*.value` — priority_*, contribution — contribution_*, weight — из manifest.
Сумма contribution равна priority_score с допуском существующего validator.
Список правил и порогов показывается вместе с summary, без интерпретации frontend.

## 8. Графы

`GET /runs/{run_id}/nodes/{gid}/graph?hops=1&node_limit=100&edge_limit=350`
→ 200 `GraphResult`. hops=1 (default) или 2, node_limit 1–100,
edge_limit 1–350. Лимиты передаются целыми числами; превышение — 422.

Для выбора окрестности учитываются входящие и исходящие соседи; рёбра в ответе
сохраняют направление src → dst. Центр всегда включён, в том числе изолированный.
Выбор узлов: число шагов ASC, priority_score DESC, числовой gid ASC. Между выбранными
узлами рёбра выбираются по sum_kzt DESC, затем числовым src/dst ASC.
Фильтры списка на карточку и окрестность не распространяются.

total_nodes — все узлы окрестности до ограничения; total_edges — все направленные
рёбра между ними до обоих ограничений. hidden_nodes = total_nodes - nodes.length;
hidden_edges = total_edges - edges.length, включая рёбра к скрытым узлам.
Для каждого возвращённого ребра оба конца присутствуют в nodes.
Если хотя бы один hidden > 0, показать явное сообщение об усечении.

`GET /runs/{run_id}/cluster-graph?node_limit=100&edge_limit=350`
→ 200 `ClusterGraph`. Лимиты те же. Узлы — кластеры, порядок n_nodes DESC,
cluster_id ASC. Направленные межкластерные рёбра агрегируют sum_kzt и n_tx отдельно.
Внутрикластерные потоки остаются в sum_kzt_internal, петли не рисуются.
Рёбра выбираются по sum_kzt DESC, src_cluster_id ASC, dst_cluster_id ASC.
Totals относятся ко всей сети кластеров до ограничений; hidden определяется
как total минус длина соответствующего массива. Изолированные кластеры сохраняются
в множестве кандидатов. Клик на кластер открывает nodes?cluster_id=... .

Frontend использует стрелки, легенду ролей и переключатель цвета роль/кластер
в окрестности. Не скрывает seed и depth=4; обозначения дублируют цвет формой,
обводкой или подписью. Клиентский layout не должен менять данные или направление.

## 9. Выбор клиентов и экспорт

| Метод / путь | Запрос | Ответ |
| --- | --- | --- |
| `GET /runs/{run_id}/selection` | — | 200 `Selection` |
| `PUT /runs/{run_id}/selection` | `PutSelectionBody` | 200 `Selection` |
| `GET /runs/{run_id}/selection/export` | — | 200 CSV |
| `GET /runs/{run_id}/exports/{filename}` | filename из `ExportFile` | 200 CSV |

Selection — один сохранённый список на run для локального рабочего места;
изначально gids=[], updated_at=null. Максимум 500 уникальных gid. PUT заменяет
список атомарно, сохраняет порядок, дубли удаляет по первому вхождению. Неизвестный
gid делает весь запрос ошибочным (422 INVALID_REQUEST), превышение лимита — 422
SELECTION_LIMIT. Пустой массив очищает список. Между run выбор не переносится.

Frontend отправляет PUT последовательно; при ошибке не сообщает «Сохранено».
Одновременные изменения из разных вкладок имеют семантику последней записи;
многопользовательское редактирование не входит в v1. Повтор того же PUT безопасен.

Экспорт выбранных клиентов: отдельный `selected_nodes.csv` с колонками
gid,role,role_score,cluster_id,priority_score,evidence в порядке выбранных gid.
Пустой выбор экспортируется как CSV только с заголовком; кнопка в UI отключена.
Обязательные nodes_roles.csv, clusters.csv, top_nodes.csv скачиваются из проверенного
bundle, без фильтрации и изменения схемы. Их нельзя заменять выбранным перечнем.
Ответы: `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment`
с безопасным именем файла; финансовые числа без локализованных разделителей.
Скачиваемые CSV имеют UTF-8 BOM для распознавания кодировки в Excel. BOM добавляется
при скачивании через API и Streamlit; файлы bundle и их SHA256 не меняются.
В теле не JSON. При ошибке endpoint возвращает стандартный JSON ошибки;
frontend проверяет HTTP status перед сохранением Blob.

## 10. Ошибки

```json
{
  "error": {
    "code": "ACTIVE_RUN_EXISTS",
    "message": "Для этого набора уже выполняется расчёт.",
    "details": [],
    "retryable": false,
    "related_run_id": "00000000-0000-4000-8000-000000000002"
  },
  "request_id": "request-example-1"
}
```

| HTTP | Коды | Действие frontend |
| --- | --- | --- |
| 413 | UPLOAD_TOO_LARGE | Показать лимиты и предложить выбрать файлы заново |
| 415 | UNSUPPORTED_FILE_TYPE | Указать неподдерживаемый файл |
| 422 | INVALID_REQUEST, DATASET_INVALID, SELECTION_LIMIT | Показать сообщение и details у полей |
| 404 | NOT_FOUND | Показать отсутствие ресурса в текущем контексте |
| 409 | DATASET_NOT_READY, RUN_NOT_READY | Показать состояние ресурса, отключить недоступное действие |
| 409 | ACTIVE_RUN_EXISTS | Дать переход к related_run_id |
| 409 | IDEMPOTENCY_CONFLICT | Сообщить о конфликте запроса; не запускать новый автоматически |
| 503 | RESULT_INVALID, SERVICE_UNAVAILABLE | Не показывать непроверенный результат; дать ручной повтор |
| 500 | INTERNAL_ERROR | Сообщение об ошибке и request_id для диагностики |

Асинхронная ошибка содержимого хранится в Dataset.validation.errors при HTTP 200
GET ресурса; ошибка выполнения — Run.error при status=failed. Не смешивать
HTTP-ошибку получения ресурса с его сохранённым терминальным состоянием.
Автоматически повторяются только GET при сетевых сбоях и временных 503.
POST после неопределённого исхода повторяется только с прежним Idempotency-Key.
Импорт при потере ответа POST /datasets не повторяется автоматически: пользователь
сначала проверяет список датасетов. В v1 импорт не имеет idempotency key.

## 11. Тексты и аналитические ограничения

| Значение | Подпись |
| --- | --- |
| consolidator | Консолидация |
| distributor | Распределение |
| transit | Транзит |
| terminal | Конечный получатель в наблюдаемой выборке |
| coordinator | Структурный посредник |
| peripheral | Без выраженной роли |

- Приоритет — порядок ручной проверки, не вероятность нарушения.
- role_score — поддержка роли правилами, не вероятность виновности.
- depth=4: продолжение переводов неизвестно; отсутствие выхода не доказывает оседание.
- Seed: входящие потоки неполны. Нулевой наблюдаемый вход не равен отсутствию доходов.
- pass_through=null показывается «Не определено». При ratio_usable=false не
  использовать даже числовое отношение как подтверждение транзита.
- Период берётся из Dataset.period, а не зашивается в заголовки frontend.
- Глобально показывается ограничение: исходящие ветви, 4 колена, переводы ≥5000 KZT.
- Для synthetic всегда видимый баннер «Синтетический пример».
- Evidence, гипотезы и сообщения показываются обычным текстом, без исполнения HTML.

Backend формирует warnings по фактам: BOUNDARY_DEPTH при at_boundary,
SEED_INFLOW_INCOMPLETE при is_seed, ZERO_OBSERVED_INFLOW при in_kzt=0,
ISOLATED_NODE при in_deg+out_deg=0; SAMPLE_INCOMPLETE доступно как общее предупреждение.
Коды стабильны; русский message предназначен для отображения, не для ветвления кода.

## 12. Приёмка frontend и границы реализации

Frontend готов к интеграции, когда на моках, а затем на API проходят сценарии:

1. Три файла → validating → ready → запуск → succeeded → реальные данные экрана.
2. Ошибка файла показывает поле/причину; расчёт не доступен. Техническая ошибка
   расчёта показывает failure и позволяет создать новый запуск.
3. Повтор запроса запуска с тем же ключом не создаёт дубль.
4. Любой gid находится независимо от фильтров; неизвестный gid даёт 404-экран.
5. ID `9007199254740993` сохраняется точно во всём пути: URL, граф, выбор, CSV.
6. Изолированный узел присутствует в карточке и графе; depth=4 и seed имеют оговорки.
7. Полные прямые связи доступны при усечённом графе; направление и суммы совпадают.
8. Top имеет исходные ranks; фильтры не меняют глобальный рейтинг.
9. Выбор сохраняется после перезагрузки; другой run имеет отдельный список.
10. Скачиваются три обязательных CSV и отдельный перечень выбранных клиентов.
11. Повреждённый результат, пустой список, медленная сеть и сетевой сбой имеют
    разные состояния; старый ответ не перезаписывает более новый экран.
12. Полный CLI pipeline из README остаётся воспроизводимым независимо от frontend.

Моки должны реализовать те же URL, формы ошибок и TS-типы. Нужны сценарии success,
invalid upload, failed run, empty filters, missing gid, isolated node, boundary,
null ratio и truncated graph. Синтетические данные моков обозначаются явно.
Этот документ и типы не являются mock server. Реализация API находится в backend/.

Реализованные изменения backend: независимое от визуализации чтение bundle,
реестр датасетов/запусков и устойчивое хранение selection, адаптация
pipeline к заранее выделенному run_id, worker и HTTP-адаптеры,
единые ошибки. Значения ролей и обязательные CSV берутся из существующих
contracts; алгоритмы не дублируются в frontend. При расхождении с текущим кодом
новые возможности считаются запланированными до проверки интеграционными тестами.
