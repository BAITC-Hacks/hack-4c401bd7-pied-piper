# Методология и контракт результата

Актуальные реализации: [engine](../backend/core/engine.py), [reporting](../backend/core/reporting.py), [контракт v1.0.0](../backend/core/contracts.py). Правила эвристические; баллы не являются вероятностями. Наблюдаются только переводы июля 2026 от 5 000 KZT по исходящим ветвям от seed до depth=4.

## Признаки и сообщества

Направленный граф содержит всех клиентов, в том числе изолятов. Степени считают связи с контрагентами, суммы и n_tx — разные признаки. PageRank взвешен суммой; betweenness приближён по максимум 128 опорным узлам на направленных невзвешенных кратчайших путях: деньги не трактуются как расстояние.

Louvain работает внутри слабых компонент на ненаправленной проекции, веса встречных направлений складываются. Seed алгоритмов =42. Компоненты и кластеры нумеруются по убыванию размера, затем по минимальному числовому gid. Изолят получает отдельную компоненту и кластер.

`pass_through=out_kzt/in_kzt`, при нулевом входе NULL. Отношение пригодно для scoring только при положительном входе, не для seed и не на depth=4. `seed_distance` — число исходящих шагов от ближайшего seed; недостижимость — NULL. `bridge` — доля уникальных соседей вне кластера, умноженная на нормированное число таких соседей.

Нормализация: `N(x)=clip(log1p(x)/Q95_positive(log1p(x)),0,1)`. Если положительных значений нет, scale и нормированные значения равны нулю. Квантили и масштабы рассчитываются на полном наборе и не меняются при фильтрации UI.

## Допуски и score ролей

Обозначения: `I/O=N(in_deg/out_deg)`, `Vi/Vo=N(in_kzt/out_kzt)`, `Ti/To=N(in_tx/out_tx)`, `B/P=N(betweenness/pagerank)`. `fan_in=in_deg/(in_deg+out_deg)`, `fan_out=out_deg/(in_deg+out_deg)`; у изолята оба 0.

| Роль | Допуск | Базовая оценка |
| --- | --- | --- |
| consolidator | in_deg ≥ max(2, ceil(Q75 положительных in_deg)) | 0,40I + 0,25Vi + 0,15Ti + 0,20fan_in |
| distributor | out_deg ≥ max(2, ceil(Q75 положительных out_deg)) | 0,40O + 0,25Vo + 0,15To + 0,20fan_out |
| transit | Есть вход/выход, пригодное отношение r>0; balance=min(r,1/r) ≥ Q75 среди пригодных кандидатов | 0,45balance + 0,35min(Vi,Vo) + 0,20min(Ti,To) |
| terminal | depth<4, in_deg>0, out_deg=0, вход ≥ Q75 положительных входящих сумм | 0,50Vi + 0,25I + 0,25Ti |
| coordinator | Есть вход/выход, betweenness>0 и ≥ Q75 положительных значений; ≥2 внешних соседей или ≥2 отправителя и ≥2 получателя | 0,45B + 0,20P + 0,20bridge + 0,15min(I,O) |
| peripheral | Нет допустимой содержательной роли | 1 до ограничения поддержки роли |

При отсутствии выборки для порога соответствующая роль недопустима. Недопустимая роль имеет score=0 и непустую причину. Из допустимых выбирается максимальная оценка; точное равенство разрешается порядком consolidator, distributor, transit, terminal, coordinator.

Пусть s1/s2 — лучшие две допустимые оценки (s2=0, если второй роли нет). Поддержка основной роли `role_score=s1×(1−0,5×s2)`, разрыв `role_margin=s1−s2`. Альтернатива и её score сохраняются. Peripheral не конкурирует с содержательными ролями; для него margin=0, альтернатива=NULL. У boundary и изолятов итоговая поддержка ограничена 0,5.

В проверенном официальном результате:

| Порог | Значение |
| --- | ---: |
| in_degree_min | 2 |
| out_degree_min | 3 |
| terminal_in_kzt_min | 166 819,70 KZT |
| transit_balance_min | 0,591788904179305 |

Это вывод из данных, не константы для подстановки в алгоритм. Точные значения конкретного запуска — в run.json. Порог transit допускает заметное расхождение объёмов; «транзит» не доказывает атрибуцию или скорость движения средств.

## Приоритет

- Структура = 0,60B + 0,25P + 0,15bridge; вес 0,35.
- Близость seed = 1/(1+seed_distance), 0 при недостижимости; вес 0,20.
- Масштаб = N(in_kzt+out_kzt); вес 0,30.
- Поддержка = role_score, для peripheral 0; вес 0,15.

Priority — сумма четырёх взвешенных вкладов. Сортировка: priority по убыванию, gid численно по возрастанию; без предварительного округления. UI показывает priority×100, экспорт — [0,1]. Why называет два крупнейших вклада; точное равенство разрешается порядком компонентов выше.

## Выгрузки

| Файл | Обязательные поля |
| --- | --- |
| nodes_roles.csv | gid, role, role_score, cluster_id, priority_score, evidence |
| clusters.csv | cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis |
| top_nodes.csv | rank, gid, role, priority_score, why |

CSV: UTF-8, LF, без index, идентификаторы signed int64. Evidence — 1..200 символов с числами и оговоркой. Top содержит ≥20 клиентов на официальном наборе. Кластерная сумма включает каждое внутреннее направленное ребро один раз; top_gids — до пяти лидеров через `|`.

Полные метрики и исходные рёбра включаются в Parquet. В UI gid превращается в строку для сохранения точности. SHA256 фиксирует точные байты; изменение окончаний строк нарушает хеш, даже если значения не изменились.

## Масштабирование до порядка миллиона узлов

Это план, не реализованная возможность. Потребуются пакетное чтение/агрегация Parquet, компактное CSR-представление или специализированный графовый движок вместо Python-объектов NetworkX, ограниченный бюджет приближённой центральности и кластеризации, предрасчёт метрик отдельно от UI и индексированный доступ к ограниченному окружению. Нужны отдельные замеры памяти/времени и проверка сохранения объяснимости на большом наборе.
